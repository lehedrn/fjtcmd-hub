### 类型 1：单表 (crud) — sys_student

### 类型 2：树表 (tree) — sys_product
**脚本组成：**
- `sql/create_product.sql` — 建表 DDL
- `config/gen_product.yml` — 配置：`tplCategory: tree`，需要指定树表三要素

**树表三要素**（必须明确指定）：
| 配置项 | 含义 | 对应 sys_product |
|--------|------|-----------------|
| `treeCode` | 树节点编码（通常是主键） | `product_id` |
| `treeParentCode` | 父节点引用字段 | `parent_id` |
| `treeName` | 节点显示名称 | `product_name` |

### 类型 3：主子表 (sub) — sys_customer（主）+ sys_goods（子）

## 我的疑问

**问题 1：树表 - ancestors 字段**
RuoYi 标准树表（如 sys_dept）有个 `ancestors` 字段存储所有祖先节点路径（如 `0,100,200`），用于快速查询某节点的所有子孙。sys_product 没有这个字段。这不影响树表生成，但深层查询效率会低一些。**是否需要补上 `ancestors` 字段？还是就按现有 DDL 生成？**

**问题 2：主子表 - SQL 文件组织**
sys_customer 和 sys_goods 两张表是放在**一个 SQL 文件**还是**两个**？
- 一个文件：CLI 一次解析两张表，自动关联
- 两个文件：CLI 只支持 `--sql` 单文件，需要改 CLI 或手动合并

我倾向**一个文件**。

**问题 3：主子表 - 字段命名**
sys_goods 中有几个字段需要确认：
- `name` → Java 属性名 `name`，太通用。是否改为 `goods_name`？
- `date` → Java 属性名 `date`，类型为 `Date`。语义不明，是否改为 `produce_date` 或 `goods_date`？
- `type` → 自动推断为 select 组件，但没有指定字典。是否需要建字典？

**问题 4：主子表 - 子表字段定制**
sys_goods 的 `price`（decimal(6,2)）、`weight`（int(5)）等字段，是否需要在 YAML 中做定制（比如指定查询方式、字典等）？还是就保持自动推断？

**问题 5：配置文件的组织**
三种类型是分别写**3 个独立的 YAML 文件**，还是合成**1 个**？
- 独立文件：每次生成时指针对一个，清晰明了
- 合成一个：CLI 目前只支持一个 `--config`，但可以在一个 YAML 中为不同表配置不同的 `tplCategory`
