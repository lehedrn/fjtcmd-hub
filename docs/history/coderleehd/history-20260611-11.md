### 2.2 模式识别与优化

**scripts/analyze_patterns.py**
- 分析历史执行记录
- 识别高频模式
- 计算模式置信度
- 生成优化建议

**示例模式**：
```json
{
  "pattern_id": "field_inference_phone",
  "description": "用户提到'电话/手机' → 字段名 phone/phonenumber，类型 VARCHAR(20)",
  "confidence": 0.98,
  "occurrences": 15,
  "success_rate": 1.0,
  "last_used": "2026-06-11"
}
```

**优化流程**：
1. 每次执行后，`analyze_patterns.py` 分析新数据
2. 如果某模式置信度 > 0.9，提升优先级
3. 如果某模式连续失败 3 次，标记为"需改进"
4. 生成报告到 `learnings/pattern_report.md`

### 2.3 项目约定自动检测

**scripts/detect_conventions.py**

自动扫描项目，检测：
- 新增/修改的模块
- 变化的包名规范
- 新的字典类型
- 代码风格变化
- 新增的工具类

**检测逻辑**：
```python
def detect_conventions():
    return {
        "modules": scan_modules(),           # 扫描 Maven 模块
        "packages": scan_packages(),         # 扫描包名规范
        "dictionaries": scan_dictionaries(), # 扫描字典类型
        "base_entities": scan_base_entities(), # 扫描基类字段
        "utils": scan_utilities(),           # 扫描工具类
    }
```

**与 project-conventions.md 对比**：
- 生成 `conventions_diff.md` 报告变化
- 提示用户是否更新 `project-conventions.md`
- 自动更新或手动确认

```python
def self_diagnose():
    issues = []
    
    # 检查配置
    if config_outdated():
        issues.append({
            "type": "config",
            "severity": "high",
```

## 六、风险与注意事项

### 风险 1：学习过度
- **问题**：skill 可能过度拟合特定用户的习惯
- **解决**：设置学习衰减因子，定期清理低频模式

### 风险 2：错误学习
- **问题**：用户偶然的纠正可能被错误学习
- **解决**：要求多次确认，低置信度模式需要人工审核

### 风险 3：性能开销
- **问题**：频繁读写 learnings 影响性能
- **解决**：异步保存，批量更新，使用缓存

### 风险 4：隐私问题
- **问题**：learnings 可能包含敏感信息
- **解决**：learnings/ 加入 .gitignore，不提交到仓库

**Claude**: 这是一个很好的问题。让我分析一下两种方案的优劣：

## 方案对比

### 当前方案：`docs/changelogs/{YYYY-MM-DD}.md`

**优点**：
- 按时间组织，符合"日志"的自然概念
- 容易查看"今天做了什么"
- 一天一个文件，结构简单

**缺点**：
- 同一天做多个模块时，都混在一个文件里
- 难以查找"student 模块的所有历史工作"
- 文件名看不出是什么模块

### 你的方案：`docs/changelogs/{module}/{business}.md`

**优点**：
- 按模块/业务组织，便于查找特定功能的所有工作
- 每个业务独立文件，清晰分离
- 符合项目管理思维

**缺点**：
- 丢失时间维度（什么时候做的？）
- 同一业务多次开发时：覆盖？追加？版本号？
- 如果一天做 5 个业务，就有 5 个文件

## 潜在问题

如果同一业务（如 student）被多次开发：
1. **覆盖** - 丢失历史记录
2. **追加** - 文件越来越大，难以维护
3. **版本号** - `student-v1.md`, `student-v2.md` - 复杂

## 推荐方案：混合式

**`docs/changelogs/{module}/{business}/{YYYY-MM-DD}.md`**

```
docs/changelogs/
├── demo/
│   ├── student/
│   │   ├── 2026-06-11.md    # 第一次开发
│   │   └── 2026-06-15.md    # 第二次迭代
│   ├── product/
│   │   └── 2026-06-12.md
│   └── customer/
│       └── 2026-06-13.md
└── cms/
    └── article/
        └── 2026-06-14.md
```

**优点**：
- ✅ 按模块/业务组织（易查找）
- ✅ 保留时间维度（每次开发独立）
- ✅ 同一业务多次开发不冲突
- ✅ 清晰的层级结构

**缺点**：
- 目录层级稍深
- 文件可能较多（但每个都小且聚焦）

## 其他考虑

如果选择你的方案 `docs/changelogs/{module}/{business}.md`，需要在文件内处理时间：

```markdown
---
module: demo
business: student
created: 2026-06-11
updated: 2026-06-15  # 每次更新追加
versions:
  - date: 2026-06-11
    action: 初始开发
  - date: 2026-06-15

---

# 学生管理 - 开发记录

...

## 2026-06-11 初始开发
...
```

这种方式把"历史"都放在一个文件里，适合"演进式"记录。
